## 1. 愿景（用户原话，2026-10-12）

> 一个**自下载**的、**具有保存功能**的、**自行整理**的、**多媒介 / 多媒体**的、
> **独属于自己**的、**本地化**的知识库。

拆成四个关键词：

| 关键词 | 含义 | 技术含义 |
|---|---|---|
| 自下载 | 不依赖平台的导出功能、不依赖人工搬运 | 抓取层独立于任何平台 UI |
| 具有保存功能 | 内容**永久留存**，不随链接失效 | 原始文件 + 元数据双存，本地优先 |
| 自行整理 | 系统自动分类、去重、摘要、建索引 | 分析层 + 资产索引 + 标签体系 |
| 多媒介 / 多媒体 | 图文 + 视频 + 音频 + 字幕 + 弹幕 全都要 | 统一资产 schema，覆盖多种媒体类型 |
| 独属于自己 / 本地化 | 数据在**自己的服务器/云端**，不依赖第三方服务 | 自托管；外部 API 仅用于分析，不用于存储 |

## 2. 最佳使用场景（这是产品设计的北极星）

> **看到有意思的内容 → 在终端、手机或电脑上 → 通过 UI，或者更简单一点，直接告诉 AI →
> 把链接发过去 → 自由选择「单个作品」还是「这个作者的全部作品」，或者其他操作
> （评论、弹幕、收藏夹……）→ 本地化下载 → 存到自己的云端 → 系统自动归档整理。**

拆成必须满足的交互约束：

| # | 约束 | 为什么重要 |
|---|---|---|
| S1 | **多端可达**：电脑终端、手机浏览器、电脑浏览器都能发起 | 刷到东西时手上只有手机是常态 |
| S2 | **零学习成本**：不想打开网页找功能，**告诉 AI 就行** | 「更简单一点调用 AI」是明确诉求 |
| S3 | **抓取范围可选**：单作品 / 作者全部 / 合集 / 收藏夹 / 评论 / 弹幕 | 「自由选择」是明确诉求 |
| S4 | **幂等去重**：同一个链接重复提交只入库一次 | 刷到过的必须自动跳过 |
| S5 | **落盘即归档**：下载完成自动归位、生成元数据、建索引 | 「自行整理」 |
| S6 | **失效可感知**：链接挂了要报错，不能静默失败 | 归档系统的信任基础 |

对应的 Phase（详见 [PLAN.md](../PLAN.md) §6）：

| 约束 | 落在哪个 Phase |
|---|---|
| S1 多端可达 | Phase 8 入口层（Web UI + CLI + 移动端适配） |
| S2 告诉 AI 发链接 | Phase 2 kb-hub（`POST /api/ingest`，**curl 即可满足，UI 不是前置**） |
| S3 抓取范围可选 | Phase 3 B站 / Phase 4 公众号 / Phase 5 抖音 |
| S4 幂等去重 | Phase 2（asset id 用内容哈希） |
| S5 落盘即归档 | Phase 2（目录规范 + SQLite 索引） |
| S6 失效可感知 | Phase 2（任务状态机 + `error` 字段） |

### 关于 S2 的关键判断

「告诉 AI 发链接」**不需要**先做飞书/微信集成。任何能发 HTTP 请求的 AI（包括本会话的助手）
都能直接调用归档中枢的一个接口：

```
POST /api/ingest   { "url": "...", "scope": "single" | "author" | "collection" | "favorites" | "comments" }
```

这让 IM 集成从「阻塞项」降级为「锦上添花」：
Phase 1–5 完全不需要任何 IM 凭据；Phase 8 再接飞书做推送与提醒。
详见 [PLAN.md](../PLAN.md) ADR-002 与 §11。

## 3. 近期目标（Near-term）

**构建一套抖音 / B站 / 公众号的服务器端下载功能，并且必须可扩展。**

| 平台 | 必须支持的范围 | 备注 |
|---|---|---|
| **B站** | 单个视频、UP 主全部投稿、合集、**收藏夹**、弹幕 ASS、字幕 SRT | 收藏夹需 SESSDATA，降级为可选 |
| **抖音** | 单个作品、作者主页全部、合集、话题挑战、音乐原声、关键词搜索、关注/粉丝、增量 | 增量去重是刚需 |
| **公众号** | 单篇文章（正文 + 图片本地化）、公众号「后台搜索 → 全量历史」 | 全量需自有可扫码公众号 |
| 公众号以外 | — | 近期不做，接口先留好 |

**可扩展性的具体含义**（写进验收标准，不是口号）：

1. 新增一个平台 = 新增**一个 adapter 文件** + 一行注册，不改中枢代码
2. 新增一种**媒体类型**（如音频、图文）= 只改 asset schema 的 `files` 字段
3. 新增一种**入口**（CLI / Web / IM / 浏览器插件）= 只实现「调用 `/api/ingest`」这一件事
4. 新增一种**存储后端**（本地盘 / 对象存储 / NAS）= 只实现一个 storage 接口

## 4. 远期目标（Long-term，不在近期范围）

| 阶段 | 目标 | 依赖 |
|---|---|---|
| L1 | 分析层跑通：ASR 转写 → LLM 摘要 → 自动打标签 → 摘要入库 | PC 端，外部 LLM API（腾讯云 ASR） |
| L2 | 知识检索：全文索引 + 语义检索，Obsidian vault 双链 | PC 端向量库 |
| L3 | 推送与提醒：飞书机器人推「你订阅的 UP 主更新了」 | 飞书自建应用 |
| L4 | 平台扩展：小红书 / 快手 / 微博 / YouTube / B站番剧 | 每平台一个 adapter |
| L5 | 主动发现：基于订阅列表定时增量抓取（已在近期目标内，此处指多平台统一调度） | hub 调度器 |

> 远期目标里**唯一不能妥协的一条**：所有原始文件必须落在自己控制的存储里，
> 第三方服务只做「临时算力」，不做「仓库」。

## 5. 与现有决策的关系

本愿景**不推翻**已定的路线 C，而是把近期目标说得更明确：

- 近期目标的「抖音 + B站 + 公众号」**完全落在**路线 C 的平台覆盖内，无冲突
- 但「多端入口 + 抓取范围可选 + 统一资产 schema + 自行整理」这四条，
  **mp-tools 作为单体面板是不满足的** —— 它没有对外 API 文档、没有资产索引、没有归档语义

因此由本愿景引出 **ADR-005（归档中枢 + adapter 插件层）**，见 [PLAN.md](../PLAN.md) §2。
ADR-005 是对 ADR-001 的**收窄式细化**（下载层还是那套代码），不是推翻。

## 6. 尚未澄清的需求（Q7–Q11，需用户确认）

| # | 问题 | 影响 | 默认假设 |
|---|---|---|---|
| Q7 | 「自己的云端」指什么？VPS 本地盘 / 对象存储（腾讯云 COS、阿里云 OSS）/ NAS | 决定 storage 后端与备份策略 | 先 VPS 本地盘，预留对象存储接口 |
| Q8 | 视频文件长期留还是转写完即删 | 磁盘规划（当前余 34 GiB） | 长期留，配归档脚本 |
| Q9 | 需要多用户/权限吗 | 是否要做账号体系 | 单用户，不做 |
| Q10 | 是否需要**评论**入库（评论本身是有价值的内容） | 是否实现 comments scope 的存储 | 实现，存 JSON + 分表 |
| Q11 | 是否需要浏览器插件/右键菜单一键发送 | 入口扩展范围 | 后期做，不进近期 |
